# GitHubリポジトリをデータ保存先とした個人用メモ・日記Webアプリ構想まとめ

## 1. 全体構成のイメージ
- **フロントエンド（画面）**: ブラウザで開くメモ・日記のUI（HTML / CSS / JS など）をホスティングして配信
- **保存先（DBの代わり）**: PrivateのGitHubリポジトリ上の `.md`（Markdown）ファイル
- **バックエンド処理**: GitHub API（REST API / GraphQL API）経由でリポジトリ内のMarkdownファイルを読み書き

> 専用のバックエンドサーバやデータベースを用意せず、GitHubリポジトリを「保存先＋履歴管理」として活用するサーバレス寄りの構成。

---

## 2. GitHub保存を選ぶメリットと注意点

### メリット
- **編集履歴が残る**: `git log` でいつ・何を追記／修正したかを追跡できる
- **ポータビリティが高い**: プレーンなMarkdownファイルのため、他ツールやローカルエディタへ移行しやすい
- **コストを抑えやすい**: 小規模な個人利用であれば無料枠の範囲で運用しやすい

### 注意点
- **必ずPrivateリポジトリにする**: 日記・メモの公開を防ぐ
- **ホスティングの公開範囲に注意**: GitHub Pagesは公開向けが基本のため、非公開データを扱う場合はアクセス制御・認証を組みやすいホスティング（Vercel / Cloudflare Pages 等）も検討する
- **複数端末からの連続更新**: 短時間に連続で書き込むとコミット競合（SHA不一致など）やAPI制限に注意が必要

---

## 3. セキュリティ（トークンと認証）の考え方
- **ローカルGit操作との違い**: 手元のPC内で使うトークンと異なり、ブラウザに配信されるフロントエンドコードは閲覧・解析される前提になる
- **トークンの扱い**: ブラウザ側のJavaScriptにトークンを直接埋め込まない（サーバレス関数／環境変数経由でAPIを呼ぶなど分離する）
- **画面の認証**: URLを知られても見られないよう、自分だけがアクセスできる認証・アクセス制限を設ける
- **権限の最小化**: Fine-grained Personal Access Token 等を使い、対象リポジトリ・必要最小限の権限に絞る

---

## 4. データ管理・フォーマット案（年単位md + `## YYYYMMDD`）
- **想定ボリューム**: 1日約50文字 × 365日 ≒ 約15,000文字（十数KB程度）で、1ファイル丸ごとの取得・パースも現実的
